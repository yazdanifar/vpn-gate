# Decisions

Log of decisions. Add a dated entry whenever a unit asks the user something; never silently change one.

## Initial decisions (made with the user, 2026-10-25)
| Topic | Decision | Why / rejected |
|---|---|---|
| Core + daemon language | **Rust** workspace, used on all 4 platforms. macOS is the *first* backend. The Swift core and helper are deleted once it reaches parity. | Best TUN/Wintun/netlink/TLS ecosystem, no GC, and it cross-compiles everywhere. Rejected: Swift everywhere (immature Windows/Android toolchains) and Go (clunkier mobile FFI, GC). |
| Architecture | **Thick engine, thin UIs.** The engine owns the protocol, the tunnel, server-list and VGDat sync, and probing. On desktop the engine is a privileged daemon, and the UIs speak the existing newline-delimited JSON IPC. On Android the engine runs in-process. | No logic is duplicated across the four UIs. The SwiftUI app doesn't care what language the helper is written in, so switching mac over is cheap. |
| GUIs | **Native per OS:** macOS uses SwiftUI (existing). Windows uses **WinUI 3 + C#**. Linux uses **GTK4/libadwaita in Rust** (relm4). Android uses **Kotlin + Jetpack Compose**. | Native feel on each platform. Replaces the earlier Flutter choice. The Linux UI can reuse the Rust IPC types directly. |
| Android ↔ Rust | **UniFFI**: one Rust API definition generates Kotlin bindings. | Rejected: hand-written JNI (verbose and error-prone). |
| Platform secrets/login | These stay in each UI: Keychain + SMAppService on mac, Credential Manager/DPAPI + a startup task on Windows, libsecret + XDG autostart on Linux, Android Keystore. | The mac code keeps working unchanged. |
| TLS | **rustls** with a custom verifier (accepts self-signed certificates and pins the leaf DER). When "system trust" is on, it uses **rustls-platform-verifier**. | The OS trust store gives the verdict, with only one TLS implementation. Rejected: native-tls and per-OS stacks. |
| Parity safety net | **Golden vectors** exported from the Swift code, which Rust must reproduce byte-for-byte, **plus** a port of every Swift test file. | Catches a test and its code being translated wrongly together. |
| Platform order | macOS, then **Windows**, then **Linux**, then **Android**. | Largest audience first after mac. |
| Packaging | mac: the existing .pkg. Windows: **MSI via WiX**, unsigned at first, with a Windows Service, a bundled signed `wintun.dll` and a self-contained WinUI app. Linux: **.deb** with a systemd unit. Android: APK/AAB. | |
| Build | Cargo for Rust. `scripts/build.sh` keeps building the Swift app and calls `cargo` (two arches + `lipo`) for the daemon. `dotnet` builds Windows and Gradle builds Android. | |

These defaults were chosen without asking. Record them in DECISIONS.md so they can be revisited:
- tokio as the async runtime.
- The IPC stays newline-delimited JSON, with `ipcVersion` bumped to 9 for the additive requests.
- WinUI is unpackaged and self-contained, with the CommunityToolkit.Mvvm and H.NotifyIcon libraries.
- relm4 for GTK.
- Compose with a ViewModel + StateFlow.

Accepted risk: in the desktop daemon, untrusted server CSV/`.dat` parsing runs as root/SYSTEM. This is mitigated by Rust
memory safety, the existing input validation and fuzz tests (U15).


## Later decisions

- **U12, IPC v9 wire shape (2026-10-27).** New commands are request/reply: a request carries an `id`, and the answer is a
  separate line `{"reply":"<cmd>","id":N,"ok":bool,"error"?,"result"?}`. Reply lines have no `state`, so a v8 client's
  `HelperEvent` decoder fails on them and ignores them. `HELPER_VERSION` stays 8 (the Swift app compares it to decide
  on a reinstall, and the golden constants pin it); the new `IPC_VERSION` is 9 and travels as `ipcVersion` in every snapshot
  event, which is how a client detects a v9 daemon. Rejected: bumping `helperVersion` (forces a reinstall for nothing),
  and answering as events (a v8 client would show them as state changes).
- **U12, who fetches the list (2026-10-27).** The daemon does (`DatFetcher` in `vpngate-net`), including the CSV mirror,
  with its own minimal HTTP/1.0 client instead of `reqwest`: no new dependency, no chunked bodies, and `https://` goes through
  the existing rustls stack with system trust. The cache is `--cache` (default per OS, `backend::default_cache_path`), the
  shipped fallback is `--bundle`.
- **U14, the Swift app mirrors the JSON instead of sharing code (2026-10-27).** `Sources/VPNGateMac/Model` carries its own
  Codable copies of the daemon's types (copied from `VPNGateCore`, minus the matching/parsing logic) and does not import the
  engine; golden-vector tests in `Tests/App/MirrorTests.swift` keep them honest. Rejected: keeping `VPNGateCore` linked into
  the app (U15 deletes it) and generating the Swift types from the Rust ones (a codegen step for ~10 structs).
- **U14, two Swift test binaries (2026-10-27).** The app tests compile `Model/` without `VPNGateCore`, because the mirrored
  names would otherwise shadow the engine's; the engine/helper tests stay in the old binary until U15. The app tests talk to a
  scripted `FakeHelperServer` that speaks the daemon's JSON, not to a real daemon.
- **U15b, golden vectors become frozen fixtures (2026-10-27).** With the Swift engine deleted nothing regenerates `Tests/Fixtures/golden`; they stay as the reference contract for Rust, the app mirrors, and the ports in U18-U28. Rejected: porting the exporter to Rust (it would test Rust against itself).
- **U15b, release (2026-10-27).** `VERSION` is 2.0.0 and the changelog has the 2.0.0 section; the `v2.0.0` tag (which triggers the Release workflow) is left to the user.
- **U18, view models live in `VPNGate.Core` (2026-10-28).** `MainViewModel` and the IPC client are in a plain `net8.0` library with no WinUI types, so `dotnet test` runs them on any OS (CI: Windows and Linux) against a fake daemon on a real named pipe. The WinUI project is only XAML, a dispatcher hook and the tray. Rejected: tests inside the WinUI project (need a Windows runner with a UI test host).
- **U18, the tray icon is a generated glyph (2026-10-28).** H.NotifyIcon `GeneratedIconSource` (a "V" on blue) instead of a `.ico` file, until U19 turns `assets/AppIcon-256.png` into the app and tray icons.
- **U18, package versions (2026-10-28).** WindowsAppSDK 1.6.250228001, Microsoft.Windows.SDK.BuildTools 10.0.26100.1742, H.NotifyIcon.WinUI 2.3.0, CommunityToolkit.Mvvm 8.3.2, xunit 2.9.3. The x64 build only for now (ARM64 comes with the MSI in U20).
- **U19, run at login is an HKCU Run key (2026-10-28).** The app is unpackaged, so an MSIX startup task is not available; `StartupRegistration` writes `HKCU\Software\Microsoft\Windows\CurrentVersion\Run\VPNGate`. If Windows refuses, the switch reverts and a notice is shown (as UI-SPEC 8 says). Rejected: a Scheduled Task (needs elevation to create at logon for a normal user, more to clean up).
- **U19, secrets in Credential Manager, chunked (2026-10-28).** Generic credentials `VPNGate/<key>` with persistence LocalMachine. One credential holds 2560 bytes, less than a certificate in base64, so `ChunkedSecretStore` (in Core, tested) splits values over `<key>#n` entries. Rejected: DPAPI-encrypted files (not what the plan says, and not visible to the user in Credential Manager).
- **U19, certificate import uses .NET crypto (2026-10-28).** `X509Certificate2` and `RSA` parse PEM/DER/PKCS#12 and re-export PKCS#1 DER, like the Swift `CertImport`. EC, DSA and passphrase-protected PEM keys are rejected with the same messages. Rejected: delegating to the Rust engine over IPC (the daemon runs as SYSTEM and has no business seeing user key files).
- **U19, no diagnostics upload on Windows (2026-10-28).** UI-SPEC says the upload is specific to the Mac app, so the Windows Advanced tab has the mirror URL and the log only, and the disclaimer drops its diagnostics caption.
- **U19, new UI is built in code (2026-10-28).** The account editor, routing editor, Settings, History and Accounts windows are plain C# (no XAML, no `x:Bind`), because the WinUI project cannot be compiled on the macOS dev machine and code gives fewer binding errors to find on CI. The main window stays XAML. Rule reordering uses up/down buttons instead of drag.
- **U20, MSI built with WiX v4 CLI from a PowerShell script (2026-10-28).** `wix` 4.0.5 (dotnet tool) with the Util extension for service failure actions and folder removal; `<Files>` harvests the app publish output. `wintun.dll` 0.14.1 is downloaded at build time and checked against a pinned SHA-256 (not committed). The data folder is locked with a deferred `icacls` action (breaking inheritance), because `PermissionEx` cannot remove inherited ACEs. x64 only, unsigned. Rejected: `cargo-wix` (v3 toolset, less control over the app files).
- **U21, iproute2 and resolvectl instead of rtnetlink and zbus (2026-10-28).** The plan names rtnetlink and a zbus D-Bus client. The backend runs `/usr/sbin/ip` and `/usr/bin/resolvectl` behind `CommandRunner`, exactly like the macOS one runs `route`. The command lines are tested on every OS against a recording fake, there are no extra dependencies (a netlink or D-Bus stack would only be tested on a Linux runner), and `resolvectl dns/domain/default-route` calls the same `SetLinkDNS`, `SetLinkDomains ~.` and `SetLinkDefaultRoute` methods. Cost: a process per change, and a dependency on iproute2 (always present on systemd distributions; the .deb in U24 declares it). Revisit if startup latency or missing binaries show up.
- **U21, peer auth by the `vpngate` group (2026-10-28).** On Linux, with no `--uid`, the daemon admits root, members of the `vpngate` group and users whose primary group it is (`SO_PEERCRED` gid/uid, group looked up per connection with `getgrnam_r`). The macOS console-owner rule does not apply (SSH and server installs have no console). The socket is mode 0666 and the check decides, as on macOS without a uid.
- **U21, SOCKS mode uses a policy rule (2026-10-28).** `ip rule add oif <tun> lookup 2330` plus `default via <router> dev <tun> table 2330`: only sockets pinned with `SO_BINDTODEVICE` reach that table. Replaces macOS `-ifscope`.
- **U22, plain gtk4-rs instead of relm4 (2026-10-28).** The state machine is `vpngate-app-model` (no toolkit, tested on every OS), so relm4's component model would only wrap a thin layer of widgets; plain gtk4 + libadwaita keeps one fewer macro-heavy dependency and compiled and ran on the dev Mac. Rejected: relm4 (PLAN's earlier choice).
- **U22, `apps/linux` is a separate Cargo workspace (2026-10-28).** The root workspace is built on macOS and Windows where GTK is absent; `exclude = ["apps/linux"]` plus a `gtk` Ubuntu CI job (`libgtk-4-dev libadwaita-1-dev`) instead. Needs libadwaita 1.5 (Ubuntu 24.04), for `AdwAlertDialog`.
- **U22, server ids are host names (2026-10-28).** Selection and favorites key on `VpnServer::id()` (the host name), as on Windows and macOS, not on the IP.
- **U23, secrets through `secret-tool` (2026-10-29).** Passwords, proxy password, certificate and key go to the Secret Service via the `secret-tool` command (libsecret-tools), value on stdin, behind a `Run` trait tested against a recording fake: same approach as U21's `ip`/`resolvectl`. No `oo7`/D-Bus stack that could only be tested on Linux. If `secret-tool` or a keyring is missing the editor reports that saving failed. Rejected: `oo7` (async D-Bus dependency tree), an encrypted file (the plan says keyring).
- **U23, PKCS#12 added in U23b (2026-10-29).** Certificate import takes PEM/DER certificate + RSA key (PKCS#1 or PKCS#8, normalised to PKCS#1), and in U23b also `.p12`/`.pfx` through the pure-Rust `p12-keystore` 0.4 (new dependency; handles both PBES2/AES and legacy 3DES/RC2 bundles). Rejected: shelling out to `openssl` (not installed everywhere, passphrase on argv).
- **U23, accounts connect through `HelperRequest.config` (2026-10-29).** Same as Windows `Connect(ClientAccount)`: the daemon gets the whole `ConnectConfig` and reconnects by itself per the account; list servers keep the controller-side retry.
- **U23, config files (2026-10-29).** `accounts.json`, `connection_history.json` and `settings.json` sit in `$XDG_CONFIG_HOME/vpngate/`. Launch at login is `$XDG_CONFIG_HOME/autostart/vpngate.desktop` pointing at the running executable.
- **U23b, Test Connection probes the current view (2026-10-29).** One `probe` request per 8 servers so rows fill in as batches finish; the targets are the servers shown after filtering, using the listed SSL ports. Results live in the model by server id and are not persisted. Sorting by the column ranks working servers by connect time, then untested, then failed.
- **U23b, columns are saved as the visible keys in order (2026-10-29).** `Settings.list_columns`; empty means the default nine. Hidden columns are re-shown at the end of the table.
- **U25, the Android API is the IPC line protocol (2026-10-29).** `AndroidEngine` hosts the daemon's `IpcCore` and talks to it over an in-memory pipe: Kotlin calls `send(json)` and receives JSON lines (replies with `reply`, events with `state`) in a `LineListener`. The Kotlin models are mirrors of the golden-checked IPC types like the Swift and C# ones, instead of ~15 UniFFI records that duplicate them; every request validation and rule of the daemon applies unchanged. Rejected: one typed UniFFI method per operation (a second schema to keep in sync) and a hand-rolled request dispatcher.
- **U25, `vpngate-uniffi` depends on `vpngate-daemon` as a library (2026-10-29).** For `IpcCore`, `Engine` and `validate`. It also pulls the daemon's Unix/Windows-only modules, which are cfg-gated out of the Android build (`group_auth` is excluded there). Rejected: moving `engine`/`validate`/`IpcCore` into a shared crate now (a large move of tested code; revisit if the dependency gets in the way).
- **U25, socket protection is a process-wide hook (2026-10-29).** `vpngate_platform::protect::set_protector` plus `vpngate_net::connect::connect_tcp` and the UDP bind, instead of threading a binder through `StreamFactory`, `TlsStream`, `proxy` and `DatFetcher` signatures. Android has one engine per process, and on every other platform no protector is set, so the hook is a no-op. Rejected: a `SocketBinder` parameter on every stream constructor.
- **U25, the tun descriptor arrives with the plan (2026-10-29).** The session creates the tun before DHCP, but `VpnService.Builder.establish()` needs the lease. `AndroidTun` is therefore a handle without a descriptor; `AndroidNet::apply` asks the host to establish with the computed `TunnelPlan` and gives the descriptor to the tun, which then starts its raw-IP reader. The descriptor is detached from `ParcelFileDescriptor` and owned (closed) by the engine.
- **U26, the Android logic is a JVM module (2026-10-29).** `apps/android/core` has no Android types (models, IPC client, filter, route splitting, `MainModel`) so `./gradlew :core:test` runs on any JDK 17, including CI without an emulator; `:app` is only Compose, the `VpnService` and the engine glue. `settings.gradle.kts` includes `:app` only when an Android SDK is present. `MainModel` is a plain class with `StateFlow`, wrapped by a thin `AndroidViewModel`, instead of putting the logic in an `androidx` ViewModel. Rejected: all code in `:app` (needs Robolectric or an emulator to test).
- **U26, the engine lives in the application, the tunnel in the service (2026-10-29).** `EngineHub` is created once per process and survives the activity; the Rust engine calls `VpnBridge.service` to establish the tunnel and protect sockets. Before a connect the UI shows the system consent dialog, starts the service and waits (5 s) for it to attach. `protect` returns true when no service runs (no tunnel to avoid). A second connection attempt is made by the UI after 15 s, like the other clients; the engine itself makes one attempt.
- **U26, always-on restart replays the last connect request (2026-10-29).** The system starts a VPN service with no data; the service stores nothing but the last `ConnectRequest` (in SharedPreferences) and sends it. Lockdown ("Block connections without VPN") is enforced by the system for services that declare `SUPPORTS_ALWAYS_ON`; the app adds nothing.
- **U26, versions (2026-10-29).** Gradle 8.9, AGP 8.7.3, Kotlin 2.0.21 with the Compose compiler plugin, Compose BOM 2024.11.00, kotlinx-serialization 1.7.3, kotlinx-coroutines 1.9.0, JNA 5.14.0 (aar) for the UniFFI bindings. The CI runner supplies the SDK (platform 35).
